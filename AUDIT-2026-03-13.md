## P0 — CRÍTICO (crash / pérdida de datos)

### P0-1: respondTrip NO usa FOR UPDATE para queuePosition
- **Archivo**: `tolvink-api/src/freights/freights.service.ts:2473-2477`
- **Problema**: `assign()` (línea 668) usa `$queryRaw` con `FOR UPDATE` para calcular queuePosition atómicamente. Pero `respondTrip()` (línea 2473) usa `aggregate()` de Prisma sin lock. Si dos transportistas aceptan viajes del mismo chofer simultáneamente, obtienen el mismo queuePosition.
- **Impacto**: Posiciones duplicadas en la cola del chofer, orden de viajes corrupto.
- **Fix**: Reemplazar el aggregate en respondTrip con la misma query raw `FOR UPDATE` que usa assign().

### P0-2: Optimistic update sin deep copy en useFreights
- **Archivo**: `src/hooks/useFreights.jsx:145-161`
- **Problema**: Las funciones `respond()` y `start()` guardan `const prev = freights.find(...)` como referencia antes del update optimista. Si el objeto es mutado por SSE refresh antes del rollback, se restaura estado stale.
- **Impacto**: Estado de flete inconsistente después de un error + SSE concurrent.
- **Fix**: Deep copy con `JSON.parse(JSON.stringify(prev))` o `structuredClone(prev)`.

### P0-3: SSE debounce timer leak en SSEProvider
- **Archivo**: `src/providers/SSEProvider.jsx:67`
- **Problema**: El debounce de `onCatalogChanged` usa closure con `let t; return () => { clearTimeout(t); t = setTimeout(...) }`. Si el provider se desmonta antes de que el timeout fire, `t` queda colgado y ejecuta `catalogRef.current?.load()` en componente desmontado.
- **Impacto**: State update after unmount, posible memory leak en SPAs con múltiples cambios de empresa.
- **Fix**: Agregar cleanup en useEffect que llame clearTimeout al desmontar.

## P1 — ALTO (feature rota / seguridad)

### P1-1: WeighTicketConfirmModal usa "error" en vez de "err"
- **Archivo**: `src/modals/WeighTicketConfirmModal.jsx:35`
- **Problema**: `show("Ingrese toneladas válidas...", "error")` pero el store useUIStore espera `"err"` como tipo. El toast no se muestra con el estilo correcto (rojo) o no aparece.
- **Impacto**: El usuario no ve el error de validación de toneladas.
- **Fix**: Cambiar `"error"` → `"err"`.

### P1-2: confirmTripLoaded — planta non-own-fleet cae a excepción con mensaje incorrecto
- **Archivo**: `tolvink-api/src/freights/freights.service.ts:2586-2658`
- **Problema**: Línea 2586 permite `ct === 'plant'`, y línea 2601 promueve a transporter si isOwnFleet. Pero si la planta NO es own fleet, cae al throw de línea 2658 que dice "Solo transportista o productor pueden confirmar carga" — debería decir "Solo transportista, productor o planta con flota propia".
- **Impacto**: Mensaje de error confuso para plantas. Lógica correcta pero UX engañosa.
- **Fix**: Actualizar mensaje de excepción.

### P1-3: Stale closure en useCatalog promise chain
- **Archivo**: `src/hooks/useCatalog.jsx:46-52`
- **Problema**: Check de `mounted` después de la resolución del promise, pero los state updates intermedios no verifican mounted. Si el componente se desmonta mid-load, React 18 puede mostrar warnings.
- **Fix**: Usar AbortController o check mounted antes de cada setState.

### P1-4: offlineQueue replay no es atómico
- **Archivo**: `src/layout/AppLayout.jsx:212-234`
- **Problema**: `offlineQueue.getAll()` itera y ejecuta cada item individualmente. Si falla uno a mitad, items previos ya se procesaron y se borraron. El re-intento ignora items ya ejecutados → datos inconsistentes.
- **Fix**: Procesar todo, marcar fallidos para retry, eliminar exitosos al final.

### P1-5: Missing notification error handling
- **Archivo**: `tolvink-api/src/freights/freights.service.ts:137-138`
- **Problema**: `notifyAllParticipants()` no tiene `.catch()` en múltiples call sites (líneas 354, 504, 2503, 2666). Si notifications service falla, es un unhandled promise rejection.
- **Impacto**: En Node.js 18+, unhandled rejection puede crashear el proceso.
- **Fix**: Agregar `.catch(err => this.logger.error(...))` a todas las llamadas.

### P1-6: FreightAccessGuard falta en getDriverQueue
- **Archivo**: `tolvink-api/src/freights/freights.controller.ts:67-91`
- **Problema**: `getDriverQueue()` no usa `FreightAccessGuard`. Cualquier usuario autenticado podría consultar la cola de drivers de cualquier empresa si conoce el driverId.
- **Impacto**: Information disclosure — un transportista puede ver la cola de drivers de otra empresa.
- **Fix**: Agregar `@UseGuards(FreightAccessGuard)` o validar companyId del driver contra el caller.

### P1-7: OCR service sin try-catch en weigh-tickets
- **Archivo**: `tolvink-api/src/weigh-tickets/weigh-tickets.service.ts:192`
- **Problema**: `this.ocrService.analyzeFromUrl()` puede fallar (timeout, API down) sin try-catch. El endpoint devuelve 500 sin contexto.
- **Fix**: Wrap en try-catch, retornar ticket sin datos OCR + warning.

### P1-8: Web-chat sin deduplicación de mensajes
- **Archivo**: `tolvink-api/src/web-chat/web-chat.service.ts`
- **Problema**: WhatsApp usa `waMessageId` para dedup, pero web-chat no tiene mecanismo. Un retry del browser puede disparar doble procesamiento → doble ejecución de tools (crear flete, asignar, etc.).
- **Fix**: Agregar idempotency key al request de web-chat.

## P2 — MEDIO (bugs menores / UX)

### P2-1: Select component no maneja value null
- **Archivo**: `src/components/form.jsx:74`
- **Problema**: `options.find(o=>o.value===value)` — si value es null y ninguna opción tiene null, `sel` es undefined. El render puede mostrar texto vacío sin placeholder.
- **Fix**: Fallback a placeholder cuando `sel` es undefined.

### P2-2: submitDone timeout sin cleanup
- **Archivo**: `src/layout/AppLayout.jsx:204-209`
- **Problema**: setTimeout para limpiar submitDone no se cancela en unmount.
- **Fix**: Guardar ref del timeout, limpiar en cleanup de useEffect.

### P2-3: Photo upload no valida freightId antes de usar
- **Archivo**: `src/layout/AppLayout.jsx:387-414`
- **Problema**: Después de crear flete con fotos, usa `r.freightId` sin verificar `r.ok`. Si la creación falla, intenta upload con freightId undefined.
- **Fix**: Verificar `r.ok && r.freightId` antes de proceder.

### P2-4: SSE handler no valida data.id
- **Archivo**: `src/hooks/useSSE.jsx:57-62`
- **Problema**: `fh.refreshLight(data.id)` asume que data.id existe. Un evento SSE malformado crashea el handler.
- **Fix**: Guard `if (data?.id)` antes de llamar.

### P2-5: AccessScreen race condition en search
- **Archivo**: `src/screens/AccessScreen.jsx:289`
- **Problema**: `searchTimer.current` se limpia en `handleSearchChange` pero no en cleanup del componente. Si el usuario cambia de pantalla mientras hay un timer pendiente, ejecuta setState en componente desmontado.
- **Fix**: Limpiar timer en useEffect cleanup.

### P2-6: TrucksScreen race condition en tab switching
- **Archivo**: `src/screens/TrucksScreen.jsx:28`
- **Problema**: `loadTrucks()` y `loadDrivers()` se llaman sin AbortController. Cambio rápido de tabs = múltiples requests concurrentes, el último en resolver gana (puede ser el equivocado).
- **Fix**: AbortController o flag de mounted por tab.

### P2-7: ReportsScreen double-click en PDF
- **Archivo**: `src/screens/ReportsScreen.jsx:237`
- **Problema**: `if(pdfLoadingId)` no previene completamente double-click porque setState es async.
- **Fix**: Usar ref para check inmediato.

### P2-8: Timezone hardcodeado en date filtering
- **Archivo**: `tolvink-api/src/freights/freights.service.ts:409-417`
- **Problema**: `dateTo + 'T23:59:59'` asume UTC. Usuarios en UTC-3 pierden las últimas 3 horas del día filtrado.
- **Fix**: Usar la timezone del usuario o agregar offset configurable.

### P2-9: Coordenadas (0,0) aceptadas como válidas
- **Archivo**: `tolvink-api/src/whatsapp/whatsapp.controller.ts:593-596`
- **Problema**: lat/lng validated -90..90 y -180..180, pero (0,0) es "Null Island" y generalmente indica error de GPS/default.
- **Fix**: Rechazar coordenadas dentro de ±0.5° de (0,0) o flag explícito.

### P2-10: SSE participantsCache sin cleanup programado
- **Archivo**: `tolvink-api/src/sse/sse.service.ts:46-61`
- **Problema**: Entries stale solo se limpian durante reads. Si nadie consulta, quedan indefinidamente.
- **Fix**: Agregar interval de limpieza periódica.

### P2-11: isFinite check después de bounds check en coordenadas
- **Archivo**: `tolvink-api/src/freights/freights.service.ts:2835-2839`
- **Problema**: `isFinite()` se verifica DESPUÉS del bounds check. Si lat/lng es Infinity, bounds check falla pero el error no es claro.
- **Fix**: Verificar isFinite primero.

### P2-12: OCR fallback demasiado permisivo
- **Archivo**: `tolvink-api/src/ocr/ocr.service.ts:228-246`
- **Problema**: Si Claude devuelve JSON inválido, el fallback extrae texto raw con confidence 0.1. Downstream puede tratar datos corruptos como válidos.
- **Fix**: Retornar status de error en vez de datos parciales.
